# Technical Specification — UrbanAlert Damage Map (Frontend)

**Version:** 0.1.0 (draft)
**Date:** 2026-10-09
**Status:** Draft — pending review
**Functional spec:** [mapa-functional-spec.md](mapa-functional-spec.md)

---

## 1. Approach

A new route `/mapa` inside the existing app (`frontend/reportes-front`, Next.js 16 App Router, React 19, Tailwind 4, TypeScript strict). It reuses what the form's location picker already uses: `leaflet` + `react-leaflet` with OpenStreetMap tiles, loaded with `next/dynamic` and `ssr: false` (Leaflet needs `window`). **No new dependencies**: aggregation is by localidad with a small point-in-polygon (§5.3), instead of `leaflet.markercluster` / `supercluster`.

Like `/historial`, the page is a Client Component that calls the gateway from the browser. The geometry (which areas to request, how to group points) lives in pure modules under `app/lib/`, so it is unit-tested without Leaflet.

## 2. How the browser reaches each service

All calls are same-origin `fetch("/api/v1/...")`.

| Need | Path | Notes |
|---|---|---|
| Damages near a point | `/api/v1/geoespacial/reports?lat&lon&radius` | Gateway: GET only, rewrites to `/api/v1/geospatial/reports` |
| Damage information | `/api/v1/reportes/{id}` | Existing `obtenerReporte` |
| Catalog | `/api/v1/reportes/catalogo` | Existing `obtenerCatalogo` |

**Running it.** Through the compose gateway (`infrastructure/`, `http://localhost:8080/mapa`). For `npm run dev` without the gateway, `next.config.ts` gets one more rewrite, `/api/v1/geoespacial/reports` → `${GEOESPACIAL_API_URL:-http://localhost:8000}/api/v1/geospatial/reports` (T-2). It exposes only the read-only nearby query, the same one the gateway publishes, and needs no secret.

## 4. Types

```ts
// GET /api/v1/geoespacial/reports item
type DanoCercano = { reportId: string; coordinateId: string; coordinate: { lat: number; lon: number } };

type Limites = { latMin: number; latMax: number; lonMin: number; lonMax: number };

type Celda = {
  clave: string;             // `${lado}:${i}:${j}`, stable across views
  lado: number;              // nominal side in meters (grid level)
  limites: Limites;          // cell clipped to the Bogotá range
  centro: Coordenada;        // centre of the clipped cell, always inside Bogotá
  radio: number;             // meters, centre → farthest corner + 1 %, ≤ 6000
};

type Localidad = {
  codigo: string; nombre: string;
  etiqueta: Coordenada;      // interior point for the bubble (pole of inaccessibility)
  limites: Limites;          // bbox
  anillos: [number, number][][];        // [lon, lat], all rings, even-odd rule
  poligonos: [number, number][][][];    // [lat, lon] for Leaflet
};

type VistaMapa = { lat: number; lon: number; zoom: number };
```

## 5. Behaviour

### 5.1 Constants

| Name | Value | Why |
|---|---|---|
| `ZOOM_PUNTOS` | 15 | Street names visible in OSM tiles; points from here inward (functional D-4) |
| `ZOOM_MIN` / `ZOOM_INICIAL` | 12 | Whole urban Bogotá fits; bounds the number of requests (§5.2) |
| `ZOOM_MAX` | 18 | Tile limit used in practice |
| `LADO_BASE` | 8000 m | Half-diagonal 5657 m < 6000 m (Geoespacial max radius) |
| `TTL_CELDA` | 60 s | Functional BR-06 |
| `ESPERA_MOVIMIENTO` | 250 ms | Debounce after `moveend` |

The map uses `LIMITES_BOGOTA` / `CENTRO_BOGOTA` from `lib/ubicacion.ts` and the same `maxBounds` margin as `MapaSelector`.

### 5.2 Query cells (`lib/celdas.ts`) — "radius determined by the zoom level"

Geoespacial answers circles of up to 6 km, but a zoomed-out view is up to ~50 km wide. The visible area is therefore split into square cells; each cell is requested as the circle that circumscribes it.

- **Cell size depends on zoom:** `lado(z) = LADO_BASE` for `z ≤ 14`, and `LADO_BASE / 2^(z−14)` above (15 → 4000 m, 16 → 2000 m, 17 → 1000 m, 18 → 500 m). At any zoom from 14 inward a view needs about 2×2 to 3×3 cells; at 12–13 it needs more (≈12–35) because the radius cap stops the cells from growing.
- **Fixed grid anchored at the Bogotá range** (`latMin`, `lonMin`), not at the viewport: `Δlat = lado / 111 320`, `Δlon = lado / (111 320 · cos(4.28°))` (centre latitude of the range; the error across Bogotá is < 0.2 %). Cell `(i, j)` covers `[latMin + i·Δlat, latMin + (i+1)·Δlat) × [lonMin + j·Δlon, …)`. Because the grid does not move with the viewport, panning only requests the new cells, and the cache key `lado:i:j` is stable.
- **Cells are clipped to the Bogotá range**, so every centre is inside it (BR-02). The radius is the haversine distance from the centre to the farthest corner of the clipped cell, plus 1 % (Geoespacial measures on the ellipsoid, haversine on a sphere; they differ by < 0.5 %), rounded up. For an 8 km cell it is ≈ 5715 m, below 6000 (unit-tested).
- `celdasVisibles(bounds, zoom)` returns the cells of level `lado(zoom)` that intersect `bounds ∩ LIMITES_BOGOTA`.
- **Exact partition:** circles overlap, so each cell keeps only the points inside its own half-open square (inclusive on the outer edge of the Bogotá range). A point is counted once (BR-03). Points are also de-duplicated by `reportId` when merging, as a guard.
- **Nesting:** sizes halve per level, so the cell `(i, j)` of size `lado/2` is inside the cell `(⌊i/2⌋, ⌊j/2⌋)` of size `lado`. When zooming in, a cell is served from a fresh cached ancestor by filtering its points, with no request.

### 5.3 Aggregation by localidad (`lib/localidades.ts`)

**Data.** `public/localidades.geojson` is generated once with `python3 scripts/localidades_geojson.py <folder with Loca.shp> public/localidades.geojson` from the SDP shapefile (MAGNA-SIRGAS geographic, used as WGS84; difference < 1 m). The script (standard library only) reads `.shp`/`.dbf`, simplifies each ring with Douglas-Peucker at 0.00005° (~5 m: 57 840 → 6 944 vertices, 0.9 MB → 153 KB), rounds to 6 decimals, and stores per localidad: `codigo`, display `nombre` (with accents), bbox `limites`, and `etiqueta`, the pole of inaccessibility (polylabel) so the bubble is always inside the localidad. Checked against the original polygons: 0.03 % of 20 000 uniform points change localidad, all next to a boundary.

**Loading.** The page loads the file once (`cargarLocalidades`, same origin, served by Next from `public/`). If it fails, a banner offers retry; points from `ZOOM_PUNTOS` still work.

**Which data is loaded.** Below `ZOOM_PUNTOS`, the localidades whose bbox intersects the view are "visible". Their bboxes are passed to `useDanosVisibles` as `areas` and loaded completely (cells of §5.2), besides the view itself, so each bubble shows the localidad's total. `estadoDe(bbox)` reports `lista | cargando | fallida` for an area.

**Counting.** `contarPorLocalidad` assigns each point to the first localidad that contains it (bbox pre-check, then even-odd ray casting over all rings, which handles holes and multi-part polygons). Points are always assigned against the **full** list of localidades, never only the visible ones. The assignment is memoised per point object in a `WeakMap` keyed by the localidades list, so re-renders do not repeat it and a result computed against another list is never reused. Points in no localidad are not counted.

**Rendering.** Below `ZOOM_PUNTOS`, each visible localidad gets a `Polygon` outline (gray, weight 1.5, fill opacity 0.05) with a sticky `Tooltip` with its name, and a `Marker` with an `L.divIcon` bubble at `etiqueta`: diameter `32 + 10·log10(n)` px, red, gray when 0, "…" while loading. The description ("Suba: 2.214 daños", "(conteo parcial)" if a cell failed) goes inside the icon HTML (`title`, `aria-label`), because react-leaflet does not update a marker's `title`/`alt` after creation. Click → `fitBounds(bbox, { maxZoom: ZOOM_PUNTOS })`.

**Attribution.** The tile layer's attribution is extended with "Localidades: SDP, Datos Abiertos Bogotá (CC BY 4.0)".

### 5.4 Data flow (`useDanosVisibles`)

1. `MapaDanos` reports `{ bounds, zoom }` on `moveend` (covers zoom and pan), debounced 250 ms.
2. The hook computes the visible cells. For each one it uses, in order: a fresh cached cell, a fresh cached ancestor (filtered), or a request `listarCercanos(centro, radio)`, then filtered to the cell.
3. Requests in flight are **not** aborted when the view changes: they finish and go to the cache, so a view that changes and comes back does not repeat them (verified in the browser: aborting caused duplicate requests). They are aborted only when the map unmounts. A cell leaves the in-flight set only when the response it requested is already in state (each request has a sequence number and each cache entry records the request that wrote it); removing it when the response arrives let an intermediate render request it again. The browser queues requests beyond its per-host limit; no extra limiter.
4. Returns `{ puntos, cargando, celdasFallidas, reintentar }`. `puntos` merges the visible cells that loaded; failed cells do not hide the others (functional §6). `reintentar` re-requests only the failed cells.

The cache lives in a `useRef` (`Map<clave, { puntos, hora }>`), and entries older than `TTL_CELDA` are ignored and replaced.

### 5.5 Rendering (`MapaDanos`)

- `MapContainer` with `preferCanvas` (points drawn on a canvas), `minZoom 12`, `maxZoom 18`, `maxBounds` like the picker.
- `zoom < ZOOM_PUNTOS`: localidad outlines and bubbles (§5.3).
- `zoom ≥ ZOOM_PUNTOS`: one `CircleMarker` per point (radius 7, same red as the picker). Click opens a `Popup` with `<DetalleDano reportId=… coordenada=… catalogo=… />`.
- Points are drawn for every loaded cell of the view; off-screen points are harmless.

### 5.6 Popup (`DetalleDano`)

- `useCarga((signal) => obtenerReporte(reportId, signal), reportId)`: requested only when the popup opens (it is mounted with the popup).
- The catalog is loaded once by the page (`obtenerCatalogo`). If it failed, codes are shown as they come.
- Shows category – type, description, state (`nombreEstado`), level (`nombreNivel`), date (`formatearFecha`), image if `urlImagen`, and coordinates (`formatearCoordenada`).
- 404 → "No hay un reporte registrado para este punto". Other errors → message and retry.

### 5.7 Page and URL (`/mapa`)

- The initial view comes from `?lat&lon&zoom` (`leerVista`): numbers, centre inside Bogotá, zoom clamped to 12–18. Otherwise `CENTRO_BOGOTA`, zoom 12.
- After each settled movement the URL is updated with `window.history.replaceState` (`escribirVista`, 5 decimals). Next's router is not used, so no navigation or re-render is triggered.
- `useSearchParams` is wrapped in `Suspense`, same as `/historial`.
- The map fills the viewport. Status is a small overlay over the map (count of damages in view, loading indicator, banner for failed cells with "Reintentar", empty message when the view has no damages and nothing is loading or failed). There is no page header, so the same page works standalone and inside the welcome page's iframe.

### 5.8 Welcome page (`/`) and form route

- `app/page.tsx` becomes the welcome page (Server Component, no client state). Same classes as the form: `main` with `min-h-screen bg-gray-100 p-6`, a white card (`rounded-xl bg-white p-8 shadow-lg`), `h1 text-3xl font-bold text-gray-900`, helper text `text-gray-500`, and the primary button with the form's submit classes (`rounded-lg bg-black py-3 font-medium text-white hover:bg-gray-800`) as a `next/link` to `/reportes/nuevo`.
- The map is `<iframe src="/mapa" title="Mapa de daños reportados">` inside the card, full width, rounded border, fixed height (`h-[60vh]`, min 360 px). Same origin: no gateway or header changes (neither nginx nor Next send `X-Frame-Options`).
- The form moves with `git mv app/page.tsx app/reportes/nuevo/page.tsx`; only relative imports change (`./components` → `../../components`, `./lib` → `../../lib`). Its markup and classes are untouched.

### 5.9 Theme

`app/mapa/layout.tsx` sets `bg-gray-100 text-gray-900` like `/historial`. Bubbles and popup content use explicit colors.

## 6. Error handling

`listarCercanos` uses `obtenerJson`, so failures are `ApiError { status, message }`. Geoespacial's `{code, message}` body already maps through `message`. Aborted requests are ignored. A 400 from Geoespacial would mean a bug in `celdas.ts`; it is treated like any failed cell (banner), and the unit tests guard the invariants of BR-02.

## 7. Security notes

- Read-only; nothing secret is sent or stored.
- Report fields are rendered as text (React escaping). The image is shown with `<img src={urlImagen}>`, as in `/historial`.
- The dev rewrite (T-2) exposes nothing the gateway does not already publish.

## 8. Testing

| Level | Tool | What |
|---|---|---|
| Unit | Vitest | `celdas.ts`: centres inside Bogotá, radius ≤ 6000, every point of `bounds ∩ Bogotá` falls in exactly one cell, cell size per zoom, ancestor nesting. `localidades.ts`: point in polygon with a hole, known places in the real GeoJSON (Plaza de Bolívar → La Candelaria, Parque 93 → Chapinero, El Dorado → Fontibón…), a point in Soacha → none, every label inside its localidad, totals ignore points outside. `vistaMapa.ts`: valid and invalid params. `listarCercanos`: query string. |
| Hook | Vitest + `renderHook`, mocked `fetch` | Cache hit within TTL, ancestor reuse on zoom-in, partial failure + retry of only failed cells, cells that leave the view finish into the cache (no repeat), abort on unmount, areas loaded whole with `estadoDe` |
| Component | Vitest + Testing Library | `DetalleDano`: loading, data with labels, 404 message, error + retry |
| Manual E2E | Compose + browser | Bubbles at 12–14, points from 15, click bubble zooms in, popup with a real report, URL sharing, partial failure (stop `geoespacial-api`) |

Leaflet rendering itself (`MapaDanos`) is checked manually; jsdom has no layout for Leaflet.

Done when: `npm test`, `npx eslint app`, `npm run build`, and the manual pass recorded in `mapa-verify.md`.

## 9. Out of scope / later

- "Open only" filter (functional OQ-1). When the backend offers it, it is one more filter in `listarCercanos` or one batch call after it; the cells, cache and aggregation do not change.
- Count-per-localidad endpoint in Geoespacial (functional §7.3).

| ID | Decision |
|---|---|
| T-1 | No clustering library: aggregation by localidad with the SDP polygons (`lib/localidades.ts`, pure, tested). Replaces the first screen-grid version (functional D-7). |
| T-2 | `next.config.ts` gets a rewrite for `/api/v1/geoespacial/reports` only (dev without gateway). |
| T-3 | `useCarga` moves from `app/historial/` to `app/lib/` to be shared; the two `/historial` imports are updated. No behaviour change. |

| T-4 | Fixed grid anchored at the Bogotá range with zoom-dependent cell size, so the requested radius follows the zoom and cells are cacheable. |
